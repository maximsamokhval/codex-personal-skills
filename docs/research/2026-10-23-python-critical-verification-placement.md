# Где хранить проверки критического Python-кода

Дата исследования: 2026-10-23.

## Короткий вывод

Для персонального Codex-скилла лучше принять гибридное правило:

- в рабочем коде оставлять только небольшие, стабильные и понятные правила, которые являются частью публичного поведения функции или доменного объекта;
- Hypothesis-тесты, CrossHair-оболочки, Atheris-харнесы, модели состояний, эталонные реализации и дорогие свойства хранить отдельно в `tests/` или `verification/`;
- изменение рабочего кода ради контракта предлагать отдельно и выполнять только после согласования;
- не называть успешный запуск доказательством, если инструмент лишь не нашёл контрпример за отведённое время.

Так ключевые правила остаются рядом с реализацией, но production-код не получает лишние зависимости и нагрузку от исследовательских инструментов.

## Что означают четыре инструмента

| Инструмент | Что он делает | Где держать проверку по умолчанию | Что означает успешный результат |
|---|---|---|---|
| CrossHair | Символически выполняет типизированные функции и ищет входы, нарушающие контракт | В `verification/`; контракт в рабочем коде — только если он одновременно служит стабильной спецификацией API | «Контрпример не найден в пределах анализа», не доказательство |
| Deal runtime/contracts | Проверяет предусловия, постусловия, исключения, побочные эффекты и инварианты при вызовах | Небольшие стабильные контракты можно держать рядом с функцией; дорогие и экспериментальные — отдельно | Только проверка конкретных вызовов |
| `deal prove` | Переводит поддерживаемое подмножество Python в математическую модель | Отдельный verification-проход; контракт может находиться рядом с кодом или на узкой проверочной функции | Формальное доказательство только для успешно переведённой модели и её предпосылок |
| Hypothesis | Генерирует конечное число тестовых примеров, ищет и уменьшает падающий пример; умеет генерировать последовательности действий | В `tests/`, включая state machine | Тесты прошли на сгенерированных примерах, не доказательство |
| Atheris | Coverage-guided fuzzing: мутирует байтовые входы и ведёт поиск по покрытию | Отдельный `fuzz/` или `verification/fuzz/`, вместе с corpus | За отведённый бюджет не найдено падение, не доказательство |

CrossHair прямо предупреждает, что отсутствие контрпримера не гарантирует истинность свойства. Он выполняет код с символическими значениями, работает только с детерминированным поведением и не полностью изолирует побочные эффекты ([ограничения CrossHair](https://crosshair.readthedocs.io/en/latest/limitations.html), [как работает анализ](https://crosshair.readthedocs.io/en/latest/introduction.html)).

Hypothesis описывает себя как property-based testing: он выбирает примеры из заданного диапазона, а не перебирает все значения ([официальное введение](https://hypothesis.readthedocs.io/en/latest/)). Его `max_examples` задаёт конечное число успешных случаев, после которого поиск останавливается ([настройки](https://hypothesis.readthedocs.io/en/latest/settings.html)).

Atheris основан на libFuzzer и использует покрытие для направления мутаций. LibFuzzer работает с corpus и по умолчанию продолжает поиск до ошибки или ограничения времени/числа запусков; это поисковая проверка, а не исчерпывающий перебор ([Atheris README](https://github.com/google/atheris), [LLVM libFuzzer](https://llvm.org/docs/LibFuzzer.html)).

Deal называет `prove` формальной верификацией, но одновременно отмечает режим как экспериментальный и применимый только к простым чистым типизированным функциям. Неподдерживаемая функция может быть пропущена, циклы не поддерживаются без инвариантов, а на отдельные доказательства установлен timeout ([Deal formal verification](https://deal.readthedocs.io/basic/verification.html)).

## Что стоит помещать в рабочий код

Только правила, которые действительно описывают контракт функции и полезны каждому её пользователю:

- допустимый диапазон аргументов;
- обязательное свойство результата;
- разрешённые исключения;
- отсутствие определённых побочных эффектов;
- инвариант важного доменного объекта.

Deal рассматривает контракты как часть сигнатуры и умеет использовать один контракт в runtime, тестах, линтере и формальной верификации ([Deal intro](https://deal.readthedocs.io/basic/intro.html)). Поэтому короткий контракт вида «сумма после распределения равна исходной сумме» может быть оправдан рядом с критической функцией.

Однако runtime-контракт не должен заменять обычную валидацию недоверенного ввода. Обычные `assert` — отладочные проверки, а Python `-O` удаляет их ([Python `assert`](https://docs.python.org/3/reference/simple_stmts.html#the-assert-statement), [Python `-O`](https://docs.python.org/3/using/cmdline.html#cmdoption-O)).

## Что лучше держать отдельно

В `tests/` или `verification/` следует помещать:

- Hypothesis properties и state machines;
- CrossHair-оболочки, которые импортируют рабочую функцию и формулируют специальное свойство;
- сравнение оптимизированного алгоритма с медленной эталонной моделью;
- Atheris entry point, настройки, словари и corpus;
- длительные проверки, запускаемые по расписанию;
- свойства внутренней реализации, которые не являются обещанием публичного API;
- проверки, ради которых нежелательно добавлять Deal в production dependencies.

CrossHair умеет целиться в отдельный файл, функцию или строку и поддерживает обычные `assert`, PEP 316, icontract и Deal. Это позволяет держать специальные проверочные функции отдельно ([CrossHair contracts and targeting](https://crosshair.readthedocs.io/en/latest/contracts.html), [виды контрактов](https://crosshair.readthedocs.io/en/latest/kinds_of_contracts.html)).

Hypothesis-декоратор `@given` превращает функцию именно в тест; документация показывает запуск через pytest и unittest. Поэтому помещать такие функции в production-модуль нет практического смысла ([Hypothesis quickstart](https://hypothesis.readthedocs.io/en/latest/quickstart.html)). Stateful-проверки генерируют последовательности действий и интегрируются в тестовый набор через `TestCase` ([stateful testing](https://hypothesis.readthedocs.io/en/latest/stateful.html)).

Atheris требует отдельную функцию `TestOneInput`, вызывает её многократно и инструментирует импортированные модули или функции. Инструментация функции выполняется in-place и влияет на все её вызовы в процессе, поэтому fuzz entry point нужно изолировать от обычного запуска приложения ([Atheris README](https://github.com/google/atheris)).

## Нагрузка и отключение

CrossHair сам по себе запускается отдельной командой и не добавляет runtime-нагрузку приложению. Нагрузка зависит от того, какой вид контракта выбран: PEP 316 в docstring не требует runtime-библиотеки, обычные `assert` выполняются без `-O`, Deal-декораторы оборачивают функцию.

У Deal:

- включённые контракты проверяются при вызове функции;
- тяжёлая интроспекция выполняется при первом вызове и кешируется;
- `deal.disable()` отключает проверки, но оставляет небольшой вызов обёртки;
- полное отключение до импорта декорированных функций не создаёт обёртки;
- Python `-O` также отключает контракты через `__debug__`.

Официальная документация не даёт универсального числа накладных расходов. Для горячего участка требуется локальный benchmark на реальной функции ([Deal runtime](https://deal.readthedocs.io/basic/runtime.html), [Deal performance](https://deal.readthedocs.io/details/contracts.html#performance)).

Hypothesis и Atheris не дают production-нагрузки, если остаются в тестовых/verification-файлах. Atheris отдельно предупреждает, что сбор покрытия через `coverage.py` заметно замедляет fuzzing и должен включаться только для анализа покрытия ([Atheris README](https://github.com/google/atheris)).

## Windows

- CrossHair официально указывает Windows и публикует Windows wheels. Текущий пакет требует CPython 3.9+ ([CrossHair на PyPI](https://pypi.org/project/crosshair-tool/)).
- Hypothesis официально указывает Windows и публикует Windows wheels. Текущая версия требует Python 3.11+ ([Hypothesis на PyPI](https://pypi.org/project/hypothesis/)).
- Deal распространяется как универсальный `py3-none-any` wheel и требует Python 3.8+. Основная библиотека не привязана к ОС, но дополнительный `deal-solver` следует проверять на конкретной версии Python проекта ([Deal на PyPI](https://pypi.org/project/deal/)).
- Atheris официально поддерживает только Linux и macOS, Python 3.11–3.14. На Windows скилл должен предлагать WSL, Linux-container или Linux CI, а не пытаться запускать Atheris нативно ([Atheris на PyPI](https://pypi.org/project/atheris/)). Поддержка самого libFuzzer в Windows не означает поддержку Python-обвязки Atheris.

## Важная поправка к исходному материалу

Совет «сохранять `.hypothesis/` в CI» нельзя делать правилом по умолчанию. В актуальном встроенном CI-профиле Hypothesis база выключена (`database=None`), а документация называет example database кешем, на который нельзя опираться для корректности. Критический найденный пример лучше закрепить через `@example` или обычный regression test; общий database artifact использовать только как осознанную оптимизацию ([Hypothesis settings and database](https://hypothesis.readthedocs.io/en/latest/settings.html)).

Также нельзя объединять все положительные результаты словом «доказано». Для отчёта скилла нужны разные статусы:

1. `counterexample-found` — найден воспроизводимый контрпример;
2. `passed-sampled-tests` — Hypothesis-тесты прошли на выбранных примерах;
3. `no-counterexample-within-budget` — CrossHair или Atheris ничего не нашли в заданном бюджете;
4. `proved-within-model` — `deal prove` доказал поддерживаемую формальную модель;
5. `inconclusive` — timeout, неподдерживаемая конструкция, пропуск или нестабильность.

## Рекомендуемая конструкция персонального скилла

Скилл должен быть не «обёрткой над четырьмя командами», а процессом от риска к проверке.

### Этап 1. Проектирование

1. Найти критические блоки: деньги, права доступа, распределение ресурсов, дедупликация, переходы состояния, парсинг недоверенных данных.
2. Сформулировать для каждого блока свойства: предусловия, постусловия, инварианты, сохранение величин, монотонность, идемпотентность, эквивалентность эталону.
3. Указать допущения и границы модели.
4. Решить, является ли свойство постоянным контрактом API или только проверкой реализации.

### Этап 2. Выбор проверки

- чистая детерминированная функция с типами и узким состоянием: CrossHair;
- очень простая чистая функция из поддерживаемого подмножества: дополнительно попробовать `deal prove`;
- множество структурированных входов и алгебраические свойства: Hypothesis;
- длинные последовательности команд и инварианты состояния: Hypothesis state machine;
- парсер, декодер, бинарный/текстовый протокол, native extension: Atheris;
- контракт публичной критической функции: по согласованию Deal в рабочем коде плюс отдельные Hypothesis/CrossHair проверки.

### Этап 3. Размещение

Предлагаемая структура:

```text
src/...                         # рабочий код; только согласованные стабильные контракты
tests/properties/...            # Hypothesis properties
tests/stateful/...              # Hypothesis state machines
verification/crosshair/...      # специальные контракты и обёртки
verification/fuzz/...           # Atheris entry points
verification/corpus/...         # seed corpus и сохранённые интересные входы
docs/verification/properties.md # реестр критических свойств, допущений и статусов
```

### Этап 4. Запуск и отчёт

Скилл должен:

1. сначала показать список критических свойств и предложенное размещение;
2. получить согласование перед добавлением Deal-декораторов в рабочий код;
3. установить новые зависимости только после разрешения;
4. запускать быстрые проверки локально, долгие — отдельно или в CI;
5. сохранять минимальный контрпример как обычный regression test;
6. явно писать инструмент, бюджет, покрытое свойство, допущения и один из пяти статусов выше.

## Итоговое решение

По умолчанию — **проверки в тестах и `verification/`**. В рабочий код — только короткие контракты публичного поведения критических функций, когда их ценность как документации и runtime-защиты выше зависимости и измеренной нагрузки. CrossHair, Hypothesis и Atheris не должны автоматически менять production-код. `deal prove` можно называть доказательством только после успешного результата без пропуска, в пределах явно записанной модели.
