# Конвеєр вимог із редагованими JSON-артефактами

Дата: 2026-09-11

## Мета

Зв'язати `requirements-extract`, `requirements-critic` і `specification-compiler` у три явні етапи з контрольованими проміжними результатами. На кожному етапі користувач повинен мати змогу перевірити й відредагувати дані до переходу далі.

JSON є єдиним джерелом істини. Markdown-файли є відтворюваними представленнями й генеруються з JSON.

## Межі

До змін входять:

- нейтральний версіонований контракт `requirements-pipeline/v1`;
- JSON-входи та JSON-виходи для трьох наявних skills;
- детермінована валідація, перевірка SHA-256 і посилальної цілісності;
- безпечні повторні запуски без неявного перезапису ручних правок;
- генерація Markdown-представлень;
- документація процесу в кореневому `README.md`;
- автоматизовані перевірки контрактів і наскрізного процесу.

До змін не входять:

- об'єднання трьох етапів у новий користувацький skill;
- автоматичне виправлення вимог критиком;
- неявне затвердження вимог;
- проєктування архітектури, реалізація продукту або написання продуктових тестів;
- зміна моделі даних чи процесу `iso-29148-requirements`;
- автоматичне перетворення ISO-пакета у нейтральний контракт.

## Архітектура процесу

Типовий каталог артефактів — `docs/requirements/`.

| Етап | Вхід | Редагований результат | Похідне представлення |
| --- | --- | --- | --- |
| `$requirements-extract` | вихідні матеріали | `requirements.json` | `requirements.md` |
| `$requirements-critic` | `requirements.json` | `review.json` | `review.md` |
| `$specification-compiler` | `requirements.json`, `review.json`, `baseline.json` | `specification.json` | `specification.md` |

Послідовність:

```text
матеріали
  -> requirements.json
  -> ручні правки
  -> review.json
  -> усунення зауважень і повторна критика
  -> явне затвердження людиною
  -> baseline.json із SHA-256
  -> specification.json
```

Кожен наступний етап перевіряє версію контракту, структуру та актуальність вхідних артефактів. Зміна `requirements.json` або `review.json` після затвердження робить baseline недійсним через розбіжність SHA-256.

## Контракти

### `requirements.json`

Версія схеми: `requirements/v1`.

Файл містить:

- метадані документа: стабільний ID, назву, версію та мову;
- інвентар джерел із їхніми локаторами;
- вимоги зі стабільними ID;
- невирішені питання `OPEN-*`.

Кожна вимога містить щонайменше:

- `id`;
- `type`: business goal, business rule, functional, non-functional або constraint;
- нормативне `statement`;
- `provenance`: `explicit` або `derived`;
- непорожній список `source_refs`.

Необов'язкові характеристики, наприклад актор, пріоритет, стан, поріг або часовий ліміт, зберігаються в `attributes`. Для derived-вимоги обов'язкові опорні посилання та пояснення виведення.

### `review.json`

Версія схеми: `requirements-review/v1`.

Файл фіксує SHA-256 перевіреного `requirements.json` і список знахідок. Кожна знахідка містить стабільний ID, тип, серйозність, пов'язані requirement ID, опис дефекту, докази або інтерпретації, потрібне рішення та статус.

Статуси:

- `open` — рішення відсутнє;
- `resolved` — вимогу змінено, а повторна перевірка підтвердила усунення дефекту;
- `accepted-risk` — користувач явно прийняв ризик із записаним обґрунтуванням.

Skill створює нові знахідки лише зі статусом `open`. Він не переводить їх у `resolved` або `accepted-risk` без перевірюваної зміни чи явного рішення користувача.

### `baseline.json`

Версія схеми: `requirements-baseline/v1`.

Baseline містить:

- статус `approved`;
- `approved_by` та `approved_at`;
- шлях, версію і SHA-256 `requirements.json`;
- шлях і SHA-256 `review.json`;
- область затвердження;
- кількість відкритих блокерів, рівну нулю.

Baseline створюється лише після явного твердження користувача про затвердження конкретної версії артефактів.

### `specification.json`

Версія схеми: `requirements-specification/v1`.

Файл містить:

- `invariants` з ID `INV-*`;
- `acceptance_criteria` з ID `AC-*`;
- `failure_scenarios` з ID `FAIL-*`;
- `gaps` з ID `GAP-*`;
- матрицю трасування.

Кожен елемент посилається на один або кілька затверджених `BG-*`, `BR-*`, `FR-*`, `NFR-*` або `CON-*`. Компілятор створює `GAP-*`, якщо затверджених даних недостатньо, замість вигадування поведінки.

## Поведінка skills

### `requirements-extract`

Перший запуск створює `requirements.json`, валідує його та генерує `requirements.md`.

Якщо основний JSON уже існує, skill зберігає ручні правки й записує новий результат у `requirements.candidate.json` разом із коротким описом відмінностей. Заміна `requirements.json` дозволена тільки після явного запиту користувача. Після прийнятої зміни Markdown генерується повторно.

### `requirements-critic`

Skill валідує `requirements.json`, обчислює SHA-256 і виконує незалежну перевірку без зміни вимог. Перший запуск створює `review.json` та `review.md`.

Повторний запуск записує пропозицію в `review.candidate.json`. Наявні рішення й коментарі користувача не перезаписуються. Користувач порівнює результат і явно приймає заміну. Коли відкритих блокерів немає, skill може запропонувати затвердження. `baseline.json` створюється лише після явного підтвердження.

### `specification-compiler`

До компіляції skill перевіряє:

- підтримувані версії всіх контрактів;
- структуру кожного JSON;
- посилальну цілісність ID;
- SHA-256 вимог і критики проти baseline;
- статус `approved`;
- наявність автора й часу затвердження;
- відсутність відкритих блокерів і релевантних `OPEN-*`.

Будь-яка невдала перевірка зупиняє компіляцію з точним повідомленням. Успішний запуск створює `specification.json`, валідує його та генерує `specification.md`.

## Безпечні повторні запуски

- Основні JSON-файли не перезаписуються неявно.
- При наявності основного файла нова версія отримує суфікс `.candidate.json`.
- Похідний Markdown може бути перегенерований, оскільки він не є джерелом істини.
- Заміна основного JSON потребує явної команди користувача.
- Baseline є незмінним знімком; зміни потребують нового затвердження.
- Некоректний або непідтримуваний JSON зберігається без змін, а skill повідомляє конкретні помилки.

## Розміщення контрактів

Канонічні JSON Schema зберігаються в репозиторії:

```text
contracts/requirements-pipeline/v1/
├── requirements.schema.json
├── review.schema.json
├── baseline.schema.json
└── specification.schema.json
```

Кожен skill містить копії лише тих схем, які потрібні йому для самостійної установки:

- `requirements-extract`: requirements;
- `requirements-critic`: requirements, review і baseline;
- `specification-compiler`: усі чотири.

Репозиторний скрипт синхронізує копії з канонічним каталогом. Окрема перевірка завершується помилкою, якщо копії розійшлися. Runtime-утиліти використовують лише стандартну бібліотеку Python.

## Обробка помилок

Повідомлення про помилку повинно містити файл, порушене правило та, коли можливо, JSON path або ID. Структурні помилки зупиняють поточний етап. Семантична невизначеність зберігається як `OPEN-*`, critic finding або `GAP-*` відповідно до етапу.

Частково читабельні джерела позначаються явно. Skill не заявляє, що опрацював пошкоджений, зашифрований або недоступний матеріал.

## Перевірки

Автоматизовані перевірки покривають:

- повний успішний прохід через три етапи;
- непідтримувану версію контракту;
- відсутні та дубльовані ID;
- посилання на неіснуючу вимогу або джерело;
- відкритий blocker;
- зміну вимог або критики після затвердження;
- збереження ручних правок під час повторного запуску;
- заборону неявного перезапису основного JSON;
- детерміновану генерацію Markdown;
- однаковість встановлюваних копій схем із канонічними файлами.

Перевірки орієнтуються на структуру, цілісність і спостережувану поведінку, а не на точне формулювання Markdown-тексту.

## Документація

Кореневий `README.md` отримає окремий опис триетапного процесу, таблицю артефактів і короткий приклад послідовного використання. Описи трьох skills пояснюватимуть їхні JSON-входи та виходи. Документація `iso-29148-requirements` підкреслюватиме, що його пакет залишається окремим розширеним процесом.

## Критерії завершення

Робота завершена, коли:

- кожен із трьох skills описує свою частину контракту та безпечний порядок роботи;
- усі чотири схеми валідні й синхронізовані з копіями у skills;
- runtime-утиліти проходять автоматизовані перевірки;
- наскрізний приклад створює валідні артефакти всіх трьох етапів;
- compiler відхиляє застарілий або незатверджений baseline;
- README однозначно показує перехід між трьома етапами;
- `iso-29148-requirements` не змінено й не стало прихованою залежністю.
