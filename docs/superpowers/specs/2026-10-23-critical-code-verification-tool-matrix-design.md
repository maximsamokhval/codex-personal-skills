# Обязательная матрица выбора проверок

Дата: 2026-10-23

## Цель

Усилить `critical-code-verification`: его главным результатом должен быть конкретный выбор инструмента и вида проверки для каждого критического свойства, а не общий список доступных средств.

## Основное решение

Во всех режимах skill формирует матрицу выбора. Для каждого свойства назначается ровно один основной инструмент. Дополнительный инструмент разрешён только тогда, когда даёт другой тип свидетельства и его польза объяснена.

Обязательные колонки:

| Колонка | Содержание |
| --- | --- |
| Блок и риск | Проверяемый участок и последствия ошибки |
| Свойство | Точное проверяемое утверждение и предпосылки |
| Вид проверки | Unit, property-based, differential, stateful, symbolic, proof или fuzz |
| Основной инструмент | Конкретный инструмент либо стандартный `pytest` |
| Почему он | Связь между формой свойства и возможностями инструмента |
| Дополнительный инструмент | Только независимое усиление; иначе `нет` |
| Почему не остальные | Краткое исключение явно рассматривавшихся альтернатив |
| Размещение | Конкретный файл или каталог проекта |
| Запуск | Точная команда либо помеченный шаблон, если окружение неизвестно |
| Бюджет | Число примеров, шагов, секунд или иное ограничение |
| Смысл успеха | Что именно подтверждает успешный результат и чего он не доказывает |
| Состояние | `planned-not-run` либо фактический evidence status |

## Правила выбора

Skill выбирает метод по форме свойства:

- обычное известное поведение или регрессия — примерный тест на существующем test runner, обычно `pytest`;
- свойство на множестве структурированных значений — Hypothesis property test;
- сравнение оптимизированного алгоритма с простой моделью — Hypothesis differential test;
- инвариант длинной последовательности операций — Hypothesis `RuleBasedStateMachine`;
- чистая детерминированная типизированная функция — CrossHair symbolic check;
- небольшая чистая функция из поддерживаемого подмножества — `deal prove` proof obligation;
- постоянный контракт публичной критической функции — Deal runtime contract после отдельного согласования;
- парсер, декодер, протокол или native boundary — Atheris fuzz target;
- код без точного свойства или с неконтролируемыми внешними эффектами — сначала уточнение модели либо обычные интеграционные тесты, без имитации формального доказательства.

Инструмент не выбирается только потому, что он установлен. Если обычный тест даёт достаточное свидетельство для некритичного поведения, skill не усложняет проверку.

## Поведение по режимам

### Design

Матрица создаётся до изменений в коде. Все строки получают состояние `planned-not-run`. Неизвестные сведения об окружении отмечаются явно, а команда запуска может быть шаблоном.

### Implement

Skill реализует согласованные строки матрицы, устанавливает зависимости только после разрешения и обновляет состояние каждой выполненной проверки. Найденный контрпример превращается в воспроизводимый regression test.

### Assess

Skill сопоставляет имеющиеся проверки с матрицей, показывает необеспеченные свойства, избыточные инструменты и случаи, где заявленный уровень доказательств сильнее фактического.

## Формулировка результата

После матрицы skill даёт короткий вывод:

1. какие проверки обязательны сейчас;
2. какие проверки полезны позднее или в CI;
3. какие инструменты не нужны и почему;
4. требуется ли согласование production-контракта, зависимости, WSL, контейнера или долгого запуска.

Фразы вроде «можно использовать CrossHair или Hypothesis» без выбора недопустимы. Если выбор зависит от отсутствующего факта, skill называет этот факт и даёт условное решение для каждого возможного значения.

## Границы

- Матрица не заставляет применять все поддерживаемые инструменты.
- CrossHair, Hypothesis и Atheris не называются математическим доказательством.
- `proved-within-model` допустим только после успешного proof run поддерживаемой модели с записанными предпосылками.
- Проверки недоверенного ввода и безопасности остаются обычной production-валидацией, а не `assert`.
- Atheris на Windows предлагается через поддерживаемое Linux-окружение только после согласования.

## Критерии готовности

Изменение готово, когда:

1. `SKILL.md` требует матрицу во всех трёх режимах;
2. справочник выбора однозначно связывает форму свойства с видом проверки и инструментом;
3. каждая строка выбирает один основной инструмент и объясняет альтернативы;
4. design mode не выдаёт статус выполненной проверки;
5. пример с денежным распределением выбирает Hypothesis differential/property test как основной метод и CrossHair только как обоснованное дополнительное свидетельство;
6. валидатор skill проходит, а README остаётся согласован с новым поведением.
